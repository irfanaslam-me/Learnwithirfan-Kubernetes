# Kubernetes Overview

## What is Kubernetes?

Kubernetes (also written as **K8s** — because there are 8 letters between K and s) is an open-source platform that automatically manages containerized applications.

In simple words — it is a **robot manager** for your apps running inside containers.

It handles:
- Starting your app
- Restarting it if it crashes
- Adding more copies when traffic increases
- Removing extra copies when traffic drops
- Updating your app without downtime

It was originally built by **Google** in 2014, based on their internal system called "Borg". It is now maintained by the **Cloud Native Computing Foundation (CNCF)** and is used by companies like Netflix, Airbnb, Spotify, and thousands of others.

---

## Why Do We Need Kubernetes?

### The Problem — Managing Containers at Scale

When you have just one app on one server, Docker alone is fine:

```
One Server
  └── Docker
        └── your-app container  ✅ easy to manage
```

But in the real world, things get complicated fast:

```
10 Servers
  ├── Server 1  →  3 containers
  ├── Server 2  →  5 containers
  ├── Server 3  →  2 containers
  ...
  └── Server 10 →  4 containers

Questions:
  - Which server has free space for a new container?
  - Container on Server 4 crashed — who restarts it?
  - How do containers on different servers talk to each other?
  - How do you update all 30 containers without downtime?
```

Doing this manually is impossible at scale. That is exactly what Kubernetes solves.

### Without Kubernetes vs With Kubernetes

| Situation | Without Kubernetes | With Kubernetes |
|-----------|-------------------|-----------------|
| App crashes at 3am | You wake up and restart it manually | Kubernetes restarts it automatically in seconds |
| Traffic spikes (10x users) | App slows down or crashes | Kubernetes adds more copies automatically |
| Deploy a new version | Downtime while restarting | Rolling update — zero downtime |
| One server dies | Apps on that server are gone | Kubernetes moves them to healthy servers |
| 50 containers to manage | Spreadsheet + prayers | Kubernetes handles it all |

## Kubernetes Architecture

A Kubernetes installation is called a **Cluster**. Every cluster has two roles:

```
┌──────────────────────────────────────────────────────────────────┐
│                        Kubernetes Cluster                         │
│                                                                    │
│   ┌─────────────────────────┐     ┌────────────────────────────┐  │
│   │      Control Plane      │     │       Worker Nodes         │  │
│   │       (The Brain)       │     │      (The Workers)         │  │
│   │                         │     │                            │  │
│   │  ┌───────────────────┐  │     │  ┌────────┐  ┌────────┐   │  │
│   │  │    API Server     │◄─┼─────┼──│ Node 1 │  │ Node 2 │   │  │
│   │  └───────────────────┘  │     │  └────────┘  └────────┘   │  │
│   │  ┌───────────────────┐  │     │                            │  │
│   │  │    Scheduler      │  │     │  Each node contains:       │  │
│   │  └───────────────────┘  │     │  - Your app (Pods)         │  │
│   │  ┌───────────────────┐  │     │  - kubelet agent           │  │
│   │  │ Controller Manager│  │     │  - kube-proxy              │  │
│   │  └───────────────────┘  │     │  - container runtime       │  │
│   │  ┌───────────────────┐  │     │                            │  │
│   │  │       etcd        │  │     └────────────────────────────┘  │
│   │  └───────────────────┘  │                                      │
│   └─────────────────────────┘                                      │
└──────────────────────────────────────────────────────────────────┘
```

## Control Plane — The Brain

The Control Plane is responsible for **making decisions** for the entire cluster. It does not run your apps — it manages everything.

### 1. API Server

The **single entry point** for all communication with Kubernetes.

When you run any `kubectl` command, it goes to the API Server first.

```
You → kubectl get pods
           ↓
      API Server
           ↓
      checks etcd, returns result
```

Think of it as the **reception desk** of a company. Everyone must go through it.

### 2. Scheduler

Decides **which Worker Node** should run a new Pod (your app).

It looks at:
- How much CPU/memory each node has available
- Any special requirements your app has
- Which nodes are healthy

```
New Pod requested
       ↓
   Scheduler
       ↓
   "Node 2 has the most free space — put it there"
       ↓
   Pod starts on Node 2
```

Think of it as the **HR manager** assigning tasks to the right employee.

### 3. Controller Manager

Constantly watches the cluster and makes sure the **actual state matches the desired state**.

```
You said: "I want 3 copies of my app running"
Reality:   Only 2 are running (one crashed)

Controller Manager detects this mismatch
       ↓
Creates a new Pod to bring it back to 3
```

Think of it as a **quality inspector** who keeps checking that everything is as it should be.

### 4. etcd

A fast key-value database that stores the **entire state of the cluster**.

Everything Kubernetes knows is stored here:
- What nodes exist
- What Pods are running
- What the desired configuration is

```
etcd stores things like:
  "pods/default/nginx" → { status: running, node: node-1 }
  "nodes/node-1"       → { status: Ready, cpu: 2, memory: 4GB }
```

Think of it as the **company database** — if etcd is lost, the cluster loses its memory.

## Worker Node — The Workers

Worker Nodes are the machines that **actually run your applications**. A cluster can have 1 to thousands of nodes.

### 1. kubelet

An agent that runs on every Worker Node. It is responsible for running the containers assigned to that node.

```
Control Plane → "Run this Pod on Node 2"
                        ↓
                    kubelet on Node 2
                        ↓
                    starts the container
                        ↓
                    keeps reporting status back
```

Think of it as the **on-site supervisor** — executes orders and reports back.

### 2. kube-proxy

Manages **network rules** on the node so that Pods can communicate with each other and with external traffic.

```
User Request → kube-proxy → routes to the correct Pod
```

Think of it as the **network switchboard** of each node.

### 3. Container Runtime

The software that actually **runs containers** — usually Docker or containerd.

```
kubelet says: "Start this container"
                    ↓
         Container Runtime
                    ↓
         Container is running
```

## How Everything Works Together

Here is the full flow when you deploy an app:

```
Step 1: You run → kubectl apply -f my-app.yaml
                            ↓
Step 2: API Server receives the request, saves it to etcd

Step 3: Scheduler sees a new Pod is needed
        → picks the best Worker Node
        → assigns Pod to Node 2

Step 4: kubelet on Node 2 sees it has a new Pod to run
        → tells the Container Runtime to start the container
        → container starts running

Step 5: Controller Manager watches continuously
        → if Pod crashes → creates a new one
        → if node dies   → moves Pods to healthy node
```

## Kubernetes vs Docker

A very common question: *"I already use Docker — do I need Kubernetes?"*

```
Docker alone:
  Your machine → docker run nginx
  One container, one machine, you manage everything

Kubernetes:
  Your cluster → kubectl apply -f nginx.yaml
  Many containers, many machines, Kubernetes manages everything
```

| Feature | Docker Alone | Kubernetes |
|---------|-------------|------------|
| Run containers | ✅ | ✅ |
| Auto-restart crashed containers | ❌ | ✅ |
| Spread across multiple machines | ❌ | ✅ |
| Auto-scale based on load | ❌ | ✅ |
| Rolling updates (zero downtime) | ❌ | ✅ |
| Self-healing | ❌ | ✅ |
| Load balancing | ❌ | ✅ |

**Short answer:** Use Docker to build and run containers. Use Kubernetes to manage containers in production at scale.

## Where is Kubernetes Used?

### Managed Kubernetes — Cloud Providers

In real companies, nobody sets up Kubernetes manually. They use managed services from cloud providers where the Control Plane is handled for you:

| Cloud | Service Name | Short Name |
|-------|-------------|------------|
| Amazon Web Services | Elastic Kubernetes Service | EKS |
| Google Cloud | Google Kubernetes Engine | GKE |
| Microsoft Azure | Azure Kubernetes Service | AKS |

With these, you only manage your Worker Nodes and apps — the cloud takes care of the Control Plane.

### On a Local Machine — Minikube

For learning and testing, you don't need a real cluster. You use **Minikube**.

Minikube runs a **single-node Kubernetes cluster** on your laptop inside a Docker container. The Control Plane and Worker Node are both on the same machine.

```
Your Laptop
    └── Docker
          └── Minikube container
                ├── Control Plane  (brain)
                └── Worker Node    (runs your test apps)
```

It is perfect for learning all Kubernetes concepts without needing cloud infrastructure.
